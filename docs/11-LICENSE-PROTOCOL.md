# 11 — LICENSE-PROTOCOL.md (FINAL — do not redesign)

> This is the single source of truth for how licensing works. Claude Code implements exactly
> this. Any deviation must go through QUESTIONS.md, never a silent alternative design.

## 1. Keys
- License Server holds one **Ed25519 private key** (generated once, stored as an env secret on
  Ahmed's infra only — never in any repo).
- Clinic Server builds embed the corresponding **Ed25519 public key** as a compile-time constant.
  This lets the Clinic Server verify a token's authenticity completely offline.

## 2. License key format (given to the clinic once, at sale time)
`DENO-XXXX-XXXX-XXXX-XXXX` (20 chars, base32, generated by License Server, stored hashed there —
same pattern as the linking-code hashing already used in the agent pack).

## 3. Activation flow (once per install, first run)
```
Clinic Server → POST https://license.<ahmed-domain>/activate
  { license_key, fingerprint, clinic_name }

fingerprint = sha256(stable machine identifiers: volume serial + hostname), generated locally,
never a full hardware inventory — just enough to bind one key to one install.

License Server:
  - looks up key_hash, checks status = ACTIVE, checks fingerprint slot is empty or matches
  - if a DIFFERENT fingerprint already bound → reject (one key = one install, Iron Rule 9)
  - issues signed token, stores fingerprint against the license row

← 200 { token }  (token = base64( payload + Ed25519 signature ))
payload = { clinic_id, plan, issued_at, expires_at (now + 25h), status: "ACTIVE" }
```
Clinic Server stores `token` encrypted at rest (OS keychain / DPAPI on Windows) in its local data
folder.

## 4. Heartbeat flow (every 24h, background, non-blocking)
```
Clinic Server → POST /heartbeat { token, fingerprint }
License Server: verify signature (defense in depth, key is authoritative from DB) → check status
  → issue a FRESH token (new issued_at/expires_at) or a status-changed token (SUSPENDED)
← 200 { token }  |  network/DNS failure → Clinic Server keeps using the last valid cached token
```
`expires_at` on every issued token is always **now + 25h** (1h slack over the 24h heartbeat
interval) — this is what makes short blips harmless without a special "grace" code path for them.

## 5. Grace period (real internet outages)
- If heartbeat keeps failing and the cached token's `expires_at` passes: enter **grace mode**.
- Grace mode lasts **7 days from the cached token's `expires_at`**, tracked locally
  (`license_grace_started_at`, tamper-resistant only insofar as it's not user-facing UI —
  acceptable for MVP; a determined owner turning back their clock is a low-value attack against
  their own software they already paid for).
- During grace: full functionality, a small non-blocking banner ("تعذّر التحقق من الاشتراك منذ
  N يوم — يفضل التأكد من الإنترنت").
- After grace expires with no successful heartbeat: **soft lock** (§6).

## 6. Soft lock behavior (expired grace OR explicit SUSPENDED status)
- All CREATE/UPDATE server actions across the app return a uniform `LICENSE_LOCKED` error;
  UI shows a full-screen Arabic notice ("الاشتراك متوقف — تواصل مع الدعم") with support contact
  info (configurable) and a "دخول للقراءة فقط" option.
- READ operations (view patients, visits, reports, exports) remain fully available always —
  Desktop Iron Rule 3 is absolute.
- The moment a heartbeat succeeds with status ACTIVE again, lock lifts immediately, no restart
  needed (checked on next server action after the successful heartbeat).

## 7. Explicit suspension vs grace — the one asymmetry
Suspension (Ahmed marked the clinic inactive on purpose, e.g., non-payment) applies on the
**next successful heartbeat**, with **no 7-day grace** — the clinic already had connectivity to
receive that heartbeat, so "we couldn't reach the server" doesn't apply. Grace exists only to
protect a paying, well-behaved clinic from losing function over a router outage — not to soften
an intentional suspension.

## 8. What the License Server NEVER receives
`license_key` (hash only after first activation), `fingerprint`, `clinic_name` (display only,
owner-provided at sale time), heartbeat timestamps. That's the entire data surface. No patient
name, no visit, no medical data, no financial figure ever appears in any request to this service —
enforced by the fact that the Clinic Server codebase importing `lib/services/*` never has a code
path that calls the license client with business data (code review + grep check in Phase D-hardening).
